The Staff API flow follows the complete food preparation process from the perspective of the restaurant staff.

## 1. Order display

### Request

The client sends an HTTP request, filtering results to display only received orders, in order of priority.

```shellscript
curl -X 'GET' \
  'https://bookish-potato-967rw54rwqwwfx5qq-80.app.github.dev/orders?sort=priority&order=asc&fields=table_number%7Cstatus%7Cpriority%7Cdish_ids&filter=status.eq~Received&limit=10&offset=0' \
  -H 'accept: application/json'
```

### Response

If the request was successful, the server responds with a `200` status code with the response body containing all received dishes, including all relevant information.

```json
{
  "results": [
    {
      "id": "6a3420277b22606bb2fa51c4",
      "table_number": null,
      "status": "Received",
      "priority": 1,
      "dish_ids": [
        "6a3420277b22606bb2fa510c",
        "6a3420277b22606bb2fa515f",
        "6a3420277b22606bb2fa516d",
        "6a3420277b22606bb2fa511f",
        "6a3420277b22606bb2fa5106"
      ]
    },
    {
      "id": "6a3420277b22606bb2fa51bf",
      "table_number": null,
      "status": "Received",
      "priority": 1,
      "dish_ids": [
        "6a3420277b22606bb2fa5174",
        "6a3420277b22606bb2fa515f",
        "6a3420277b22606bb2fa510c",
        "6a3420277b22606bb2fa5140",
        "6a3420277b22606bb2fa5106"
      ]
```

<Note>
  This is the step that I used for the AI validation test. Claude got descriptions right and provided some expected pieces of the curl command and response. 

  However, Claude seemed to require an Authorization token for the GET function, which the API doesn't need. It also used different syntax: status=received instead of status.eq~Received. 

  It guessed at field names, mistaking id for order\_id and items for dish\_ids. All of these mistakes would seem plausible at first glance.
</Note>
